### 1. Tool misuse (most serious first)

1. **payment-terms-optimisation/SKILL.md:25, :34** — `tco.total_cost` is fed a spend figure as `landed`: "with `tco.total_cost` to value a terms change or a discount (the same spend as `landed`, the cost of capital, a one-year horizon...)" and step 4 "run `tco.total_cost` twice on the supplier's spend in the period". `landed` must be a `landed_cost.total_cost` result: `src/services/cost/tco.py:61-125` reads `landed["components"]`, `["currency"]`, `["landed_total"]`, `["unit_landed"]`, `["landed_status"]`, `["missing"]`. Every valuation step in the skill (t1, t2, e1, e3, p2) fails or comes back unassessed.
2. **payment-terms-optimisation/SKILL.md:34, :61** — "report the present-value difference from `deal.pct_change`; never work the value out by hand". `deal.pct_change(new, base)` returns a percentage; no registered calculation subtracts two present values, so the money "present-value difference" promised in output spec :56 cannot be produced under the quality bar.
3. **payment-terms-optimisation/SKILL.md:32** — "From the cube by supplier and the contracts: each supplier's spend, contract terms and invoice terms; a gap between the two is a finding." `build_spend_cube` cuts by ONE dimension: `by=payment_terms` gives spend per term with no supplier; `by=supplier` gives no terms. Per-supplier invoice terms come from `invoice_status` (payment_terms per invoice), which the skill never names. Scenarios t3 (:13) and e3 (:36) depend on this.
4. **maverick-spend-review/SKILL.md:36** — "Groups of orders from one buyer to one supplier within `split_window_days` days ... taken from the cube by buyer and the reconciliation's order references". The cube by buyer returns totals per buyer (no orders, dates, suppliers); `invoice_reconciliation` returns invoice lines keyed by po_id with no buyer; `open_orders` (`supplier_records.py:171-173`) has order date and total but no buyer. No tool returns orders with buyer + supplier + date + amount, so the split test (t3, e3) cannot be built.
5. **maverick-spend-review/SKILL.md:33** — "take the lines with no PO line on record; sum them per currency as the result states them". `differences_by_currency` sums only *matched* lines (`invoice_reconciliation.py:176-190`); `no_po_line` rows carry only a count in `kinds` and are listed up to `MAX_LINES = 60`. The result states no such sum, so the agent must add by hand over a possibly truncated list. Also `no_po_line` means "no PO line with this item on this PO" (`:106-107`), not "invoices that arrived with no order behind them" (:10).
6. **contract-portfolio-review/SKILL.md:24 vs :36** — "Do not call search_contracts or obligation_tracker separately for the pipeline" and then step 6 "list the suppliers with spend above ... and no live contract on the register". `contract_pipeline` returns only contracts ending within the horizon (default 180 days); a supplier whose contract ends in two years is absent and would be reported as "no contract on record". Coverage (t3 :13, c2 :66) needs `search_contracts` by supplier, which the skill forbids.
7. **deal.pct_change used for a share** — `(new − base)/base` is a change, not a share; `deal.share_pct(part, whole)` exists. overbilling-investigation/SKILL.md:33 "use `deal.pct_change` for their size against the invoiced total" (difference as new, invoiced total as base gives ≈ −97%); category-strategy:25 "`deal.pct_change` for shares and changes"; contract-portfolio-review:24, :38 "share of portfolio value due within the horizon via `deal.pct_change`"; maverick-spend-review:24, :32 "`deal.pct_change` for shares"; opportunity-pipeline-review:24, :32 "the share claimed against saved via `deal.pct_change`"; spend-analysis:25 "`deal.pct_change` for shares and changes". Six skills.
8. **get_corpus_facts for item prices** — identical boilerplate in demand-aggregation/SKILL.md:26, pricing-mechanisms:32, renewal-and-exit-strategy:30, savings-methodology:28: "use `tool:get_corpus_facts` for item prices or ask the user for an extract". `get_corpus_facts` returns corpus-wide counts; demand-aggregation:24 itself says "its counts and totals cover the whole corpus and are not filtered by the item named" two lines earlier. Item prices come from `similar_items` / `supplier_items`.
9. **pricing-mechanisms/SKILL.md:41, :43, :44** — asks for arithmetic no calculation provides: "the target correlation is at least `config.thresholds.index_min_correlation`, but only compute it from a series the user supplies"; "Simulate the user's index history over ... months and a stress case ... show the price path and the cost to each party"; "Compute the marginal price at each threshold". The registry has no correlation, simulation or tier function; only `deal.pct_change` is named. The system rule is "Use this instead of doing arithmetic yourself", so quality bar :69 ("The simulation can be reproduced") cannot be met without hand arithmetic.
10. **procurement-policy-compliance/SKILL.md:37** — "Look at order history for the same supplier or category from the same requester or cost centre, using `tool:get_corpus_facts`". Corpus facts are not filtered by requester or cost centre; `open_orders` has a supplier's POs but no requester. The split check (e2 :20, m4 :62) has no data source as written.
11. **incoterms-selection/SKILL.md:41** — "Pass `incoterm` as the rule plus place, `cross_border`, the `components` the user gave ... and `duty_rate` if the user gave one." `landed_cost.total_cost` requires `lines` (unit_price, quantity, currency) and `buyer_currency` (cost.py); both are missing from the skill's input list, so the call is refused.
12. **opportunity-pipeline-review/SKILL.md:24, :33** — "`tool:get_opportunity_bucket` with the supplier and item" — the tool requires `supplier_id` and `item_id`; nothing in the skill yields an item_id. Step 3 "stalled (last movement older than `stalled_days`)" — the bucket records `detectedOn` and `reviewRequestedAt` only (`opportunity_buckets.py:86-99`); there is no movement date.

14. **supplier-offboarding/SKILL.md:24** — "`tool:extract_clauses` with `containing` "exit", "assistance", "transition", "data", "return", "handover", "minimum", "exclusiv"". `containing` is one string (`clauses.py:50`): eight filters are eight calls per contract inside a six-round loop (`agentnick_control.py:1251`). Same at overbilling-investigation:24 (five terms) and supplier-sustainability-review:24 (four terms).

### Verdict
The structure is sound but the content has not been reconciled with the tools it now names. The worst defects are in payment-terms-optimisation (its central calculation is called with the wrong input and cannot run), maverick-spend-review (its two headline patterns, splits and no-PO spend, have no data source), contract-portfolio-review (coverage is computed from a horizon-limited call it forbids widening), and a `deal.pct_change`-for-share error copied into six skills that would print nonsense percentages. Four skills carry a copied paragraph that sends the agent to `get_corpus_facts` for item prices, contradicting their own text. Scenario files lag the playbooks (stale "NOT AVAILABLE" and search/tracker expectations, placeholder data never sent, upper-case verdict labels the skill forbids), and about one scenario in eight does not even reach its own skill through the router, because strong terms such as `levers`, `saved`, `renew*`, `award*`, `pool*`, `markup`, `what is missing`, `last order` and `from 30 to` are ordinary procurement words that pull requests into the wrong playbook. Before another live run: fix the four tool-input errors, replace `pct_change` with `share_pct` where a share is meant, delete the copied corpus-facts sentence, prune the generic strong terms, and regenerate the stale expect lines.
